# 작업 과정 — AI와 함께 만든 PoC

이 PoC의 코드는 AI 코딩 에이전트(Claude Code, Claude Opus 5.5)가 작성했습니다.
저는 코드를 한 줄씩 검수하지 않았습니다. 대신 **무엇을 왜 만들지 정하고, 방향을 바꾸고,
결과를 화면과 수치로 확인하는 역할**을 했습니다. 이 문서는 그 과정을 제가 입력한 프롬프트
그대로 남긴 기록입니다. 일부 프롬프트는 면접 과정의 비공개 정보를 빼고 요지만 적었습니다.

- 기간: 2026-10-01 저녁 ~ 10-02 새벽 (한 세션)
- 시작점: 면접에서 받은 기술 질문 두 개
  1. 대용량 3D 의료 영상의 웹 렌더링 성능
  2. 서버 사이드 렌더링(SSR) 아키텍처의 과제

## 역할 분담

| 저 | AI |
|---|---|
| 모르는 것을 질문하고, 답을 듣고 다시 파고들었습니다 | 설명, 웹 검색, 근거 자료 정리 |
| 설계 방향을 정했습니다 (S3 + CDN + 부분 읽기) | 설계를 구체화하고 함정을 짚었습니다 (슬라이스 저장의 요청 폭발 등) |
| 방향이 틀렸을 때 멈추고 바꿨습니다 | 제안, 구현 |
| 직접 조작해 보고 UX 피드백을 냈습니다 | 코드 작성, 헤드리스 브라우저로 자동 측정·스크린샷 |
| 결과 수치를 보고 결론을 판단했습니다 | 측정 표, README, 커밋 |

의문을 바로 다음 질문으로 이었습니다. 아래는 입력한 순서 그대로입니다.

## 2단계 — 설계 방향을 정한 프롬프트

여기서부터는 질문이 아니라 **제 입장**을 냈습니다.

> "솔찍히 말해서 난 서버사이드 랜더링으로 영상을 전송하고 싶지 않아 왜냐면 비용이 너무 많이 들어
> 근데 대부분의 케이스가 서버사이드 랜더링을 하는거 같아서 이렇게 꼭 해야되는지 알고 싶어"

→ "계산은 서버, 렌더링은 클라이언트"라는 하이브리드 구조로 정리했습니다. 이어서 "경로 추적이 뭐야?",
"webgpu 를 쓰면 어때?"로 클라이언트 렌더링의 한계를 확인했습니다.

> "개인적으로 나는 슬라이스 데이터를 s3 에 넣고 cdn 으로 전송하는 구조를 가져가고 싶어
> s3 는 부분읽기 기능을 제공하고 있고 픽셀이 무손실 데이터 구조라서 정확한 위치를 알 수 있을거란 말이야
> 그럼 그냥 필요한 위치의 정보를 읽어서 화면을 만들 수 있을거 같거든 어떻게 생각해?"

→ **이 PoC의 핵심 아이디어입니다.** AI가 보완한 점은 다음과 같습니다.
- 무손실 *압축*을 하면 바이트 위치를 알 수 없습니다 → 블록별 압축 + 인덱스가 필요합니다
- 슬라이스 순서로 저장하면 sagittal·비스듬한 단면에서 요청 수가 폭발합니다 → 3D 블록으로 저장합니다
- 볼륨 렌더링은 결국 전체가 필요합니다 → 해상도 피라미드를 둡니다
- 같은 발상의 선례: Neuroglancer, OME-Zarr, Cloud Optimized GeoTIFF

> "이런 구성이 내가 좋아하는 방식이긴한데 다만 이렇게 했을때 너가 아까 말한 경쟁 제품들이 제공하는
> 기능을 다 똑같이 제공할 수 있을지 의심스러워 스트림트레이서 같은거도 걱정이고"

> "마지막으로 하나만 니가 플로우닉스 제품이랑 비슷하다고했던 제품에서 지원하는 기능들을 내 구조로
> 가져왔을때 가능할까?"

→ 제 아이디어를 스스로 반박해 봤습니다. 공개된 경쟁 제품 기능 목록과 하나씩 맞춰 보고,
"SSR(픽셀 스트리밍) ≠ 서버 계산"으로 정리했습니다. 포기하는 것은 기능이 아니라 픽셀 전송뿐이라는 결론입니다.

## 3단계 — 우선순위 전환

> "이걸 마무리할바엔 그냥 플로우닉스에서 내가 말한 구조를 검증용 poc 를 해보는게 더 낫겠어
> … 우선 mri 데이터를 하나 구해야될거 같은데 dicom 슬라이스 데이터를 너 구할 수 있어?"

원래는 기존 개인 프로젝트를 마무리할 계획이었습니다. 면접에서 이야기할 주제와 직접 연결되는
검증이 더 가치 있다고 판단해 바꿨습니다.

> "응 IDC에서 MRI 받는 것부터 시작하자 그 전에 해당 폴더를 git 으로 관리해줄래?"

→ 공개 4D Flow DICOM은 찾기 어려워서, NCI Imaging Data Commons(공개 S3 버킷)의 실제
MRI로 대체했습니다. 받아 보니 앞에서 질문으로 배운 함정들이 실제로 다 나왔습니다
(한 시리즈에 볼륨 여러 개, InstanceNumber ≠ 공간 순서, SliceThickness ≠ 간격,
믿을 수 없는 SeriesDescription).

## 4단계 — AI의 제안을 되돌린 지점

PoC 직전에 질문을 다시 읽다가 걸리는 것이 있었습니다.

> "근데 메일을 읽어보니까 ssr 아키텍처에서 고려해야할 기술적 과제와 본인이라면 어떻게 풀어나갈 것인지
> 라고 써있는데 이건 주제에 벗어난거 같긴한데"

AI는 PoC를 "SSR 렌더 서버 vs 클라이언트 렌더링" 비교 구조로 바꾸자고 제안했습니다.
그런데 회사가 **클라이언트 렌더링 성능**을 핵심 과제로 언급했다는 점이 걸렸습니다.

> (요지) 클라이언트가 직접 렌더링하고 있다면, 여기서 말하는 SSR은 서버가 영상을 렌더링한다는
> 뜻이 아니지 않을까?

→ 브라우저가 이미 대용량 볼륨을 직접 그리고 있다면, 이 회사의 "SSR"은 픽셀 스트리밍이
아니라 **서버에서 처리하고 클라이언트가 그리는** 구조일 가능성이 높다고 봤습니다. 그래서 비교 구조로
바꾸자는 제안을 받지 않고 원래 설계를 유지했습니다. 면접에서는 이 해석을 먼저 확인 질문으로 여쭤보기로 했습니다.

> "일단 아까 말한 설계대로 poc 하나 만들어보자"

## 5단계 — 구현과 측정

AI가 변환기(Python) → Range 서버(Node) → WebGL2 클라이언트 순서로 만들고, 헤드리스
Chrome으로 단면 방향별 측정을 자동화했습니다. 측정에서 **예상과 다른 결과**가 나왔습니다.

- 촬영 방향 단면에서는 블록 방식이 오히려 8배 손해였습니다 (두께 32 블록에서 한 장만 쓰기 때문)
- 블록 크기는 요청 수(지연)와 over-fetch(대역폭) 사이의 트레이드오프였습니다

"블록이 무조건 낫다"가 아니라 "단면 방향에 따라 두 레이아웃을 고르는 것이 다음 개선"이라는
결론은 이 수치에서 나왔습니다. 결과는 [README의 측정 섹션](../README.md)을 참고해 주세요.

## 6단계 — 직접 조작해 보고 낸 피드백

> "이거 조작해보고 있는데 좌우 기울기 상하기울기 조작시 슬라이스된 단면을 보고 싶지 슬라이스가
> 기울어진체로 보고 싶진 않을거 같은데 어차피 박스를 슬라이스 하는거니까 슬라이스된 각도는
> 박스를 하나 랜더링해서 보여주는게 더 좋지 않을까?"

→ 단면 화면(잘린 면을 정면으로, 화면에 맞춤)과 3D 위치 화면(볼륨 상자 + 단면)으로 분리했습니다.
3D 화면에 **실제로 받은 블록**을 함께 그려서, "필요한 부분만 받는다"는 PoC의 핵심이
그림 한 장으로 보이게 됐습니다.

## 제가 검증한 것 / 하지 않은 것

**검증한 것**
- 블록을 받아 복원한 값이 원본과 비트 단위로 일치하는지 (무손실)
- 원본 DICOM 경로가 서버에서 노출되지 않는지
- 단면 방향별 화면 (axial에서 대동맥 단면, sagittal에서 대동맥 종단, 비스듬한 단면)
- 측정 수치가 이론과 맞는지 (요청 수, over-fetch 배율, 블록 크기별 경향)
- 직접 조작하며 UX 확인

**하지 않은 것**
- 코드 한 줄 한 줄 리뷰
- 실제 S3 + CloudFront 배포, 대역폭 제한 측정
- Cornerstone3D 연동

## 돌아보며

- 좋은 결과를 낸 프롬프트는 대부분 **"왜?"와 "정말 그래?"** 였습니다. 답을 받아들이기 전에
  한 번 더 파고들거나 제 아이디어를 스스로 반박하게 했습니다 (#3, #5, #15, 경쟁 기능 점검).
- AI의 제안을 되돌린 순간(4단계)이 가장 중요했습니다. 질문의 전제를 다시 읽고 근거를 들어
  방향을 지켰습니다.
- 코드를 직접 짜지 않은 대신, 결과를 **수치와 화면으로** 검증하도록 요구했습니다. 측정에서
  예상과 다른 결과(촬영 방향 over-fetch)가 나온 것도 그 덕분입니다.
